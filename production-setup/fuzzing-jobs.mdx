---

A production fuzzing job connects ClusterFuzz to your continuous build pipeline so that fuzzing always targets the latest version of your code. Where a local or one-off job uses a manually uploaded binary, a production job reads new build archives directly from a GCS bucket as they are published, enabling automatic regression detection and fix verification across every commit.

## Prerequisites

Before creating a production fuzzing job, set up a [build pipeline](/production-setup/build-pipeline) that publishes versioned build archives to GCS. Without a pipeline, ClusterFuzz will fuzz a single static build and cannot track regressions or verify fixes.

If you want to run with a single build while your pipeline is being prepared, you can follow the standard fuzzing setup directly and switch to a continuous build later by updating the job definition.

## Creating a job definition

Create a new job on the **Jobs** page in the ClusterFuzz UI. The job definition consists primarily of environment variables that control how ClusterFuzz finds builds, runs the target, and reports bugs.

## Specifying a continuous build

To connect a job to your build pipeline, add `RELEASE_BUILD_BUCKET_PATH` to the job's **Environment String** and set `CUSTOM_BINARY` to `False`:

```
RELEASE_BUILD_BUCKET_PATH = gs://my-bucket/my-build-([0-9]+).zip
CUSTOM_BINARY = False
```

For blackbox fuzzing targets, also specify the application name and arguments:

```
RELEASE_BUILD_BUCKET_PATH = gs://my-bucket/my-build-([0-9]+).zip
CUSTOM_BINARY = False

APP_NAME = myapp
APP_ARGS = -args -to -pass -to -myapp
```

### How revision numbers are used

The `([0-9]+)` capture group in `RELEASE_BUILD_BUCKET_PATH` is how ClusterFuzz determines which build is newest and which revision a crash was introduced in. Any file in the bucket whose path matches the full expression is treated as a candidate build. The build with the highest captured number is always selected for active fuzzing.

<Warning>
  The parentheses around the revision number pattern are required. ClusterFuzz uses this capture group specifically to extract the revision number. A path like `gs://my-bucket/my-build-[0-9]+.zip` without parentheses will not work correctly.
</Warning>

## Advanced options

### Ignoring outdated builds with `MIN_REVISION`

Use the `MIN_REVISION` variable to instruct ClusterFuzz to ignore all builds below a given revision number. This is useful when you make a significant non-backwards-compatible change that causes older builds to behave incorrectly:

```
RELEASE_BUILD_BUCKET_PATH = gs://my-bucket/my-build-([0-9]+).zip
CUSTOM_BINARY = False
MIN_REVISION = 441045
```

ClusterFuzz will skip any build archive whose revision number is below `441045`.

### Linking developers to documentation with `HELP_URL`

A job can specify a `HELP_URL` so that every test case report generated by the job includes a link to developer-facing documentation. This allows you to point developers to instructions on how to interpret and act on the bugs they are assigned:

```
HELP_URL = https://example.com/how-to-fix-fuzzer-bugs
```

## Example job definitions

<CodeGroup>

```text libFuzzer + ASan
RELEASE_BUILD_BUCKET_PATH = gs://clusterfuzz-builds/zlib/zlib-address-([0-9]+).zip
CUSTOM_BINARY = False
CORPUS_PRUNE = True
```

```text libFuzzer + UBSan
RELEASE_BUILD_BUCKET_PATH = gs://clusterfuzz-builds/zlib/zlib-undefined-([0-9]+).zip
CUSTOM_BINARY = False
```

```text Blackbox fuzzing
RELEASE_BUILD_BUCKET_PATH = gs://chromium-browser-asan/linux-release/asan-linux-release-([0-9]+).zip
MIN_REVISION = 441045
CUSTOM_BINARY = False
APP_NAME = chrome
APP_ARGS = --enable-experimental-extension-apis --js-flags="--expose-gc" --no-first-run
REQUIRED_APP_ARGS = --no-first-run
TEST_TIMEOUT = 15
ADDITIONAL_ASAN_OPTIONS = allocator_may_return_null=0
```

</CodeGroup>
