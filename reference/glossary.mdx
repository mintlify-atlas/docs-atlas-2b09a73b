---
title: "ClusterFuzz Glossary: Bots, Corpus, Sanitizers, and More"
description: "Definitions for key ClusterFuzz terms: bots, corpora, sanitizers, fuzz targets, crash types, revision ranges, testcases, and more — in plain language."
---

ClusterFuzz uses a specific vocabulary across its UI, configuration, and documentation. This glossary defines each term in context so you can navigate job definitions, testcase reports, and bot logs with confidence.

<AccordionGroup>
  <Accordion title="Bot">
    A machine which runs ClusterFuzz [tasks](/reference/glossary#task).
  </Accordion>

  <Accordion title="Corpus">
    A set of inputs for a [fuzz target](/reference/glossary#fuzz-target). In most contexts, it refers to a set of minimal test inputs that generate maximal code coverage.
  </Accordion>

  <Accordion title="Corpus pruning">
    A task which takes a [corpus](/reference/glossary#corpus) and removes unnecessary inputs while maintaining the same code coverage.
  </Accordion>

  <Accordion title="Crash state">
    A signature that ClusterFuzz generates from the crash stacktrace for deduplication purposes.
  </Accordion>

  <Accordion title="Crash type">
    The type of a crash. ClusterFuzz uses the crash type to determine severity.

    **Security vulnerability types** (not limited to):

    - `Bad-cast`
    - `Heap-buffer-overflow`
    - `Heap-double-free`
    - `Heap-use-after-free`
    - `Stack-buffer-overflow`
    - `Stack-use-after-return`
    - `Use-after-poison`

    **Other crash types:**

    - `Null-dereference`
    - `Timeout`
    - `Out-of-memory`
    - `Stack-overflow`
    - `ASSERT`
  </Accordion>

  <Accordion title="Fuzz target">
    A function or program that accepts an array of bytes and does something interesting with those bytes using the API under test. See the [libFuzzer documentation](https://llvm.org/docs/LibFuzzer.html#fuzz-target) for a detailed explanation. A fuzz target is typically given the array of bytes by libFuzzer or AFL for coverage-guided fuzzing.
  </Accordion>

  <Accordion title="Fuzzer">
    A program which generates or mutates inputs of a certain format for testing a target program. For example, a program that generates valid JavaScript testcases for fuzzing a JavaScript engine such as V8.
  </Accordion>

  <Accordion title="Fuzzing engine">
    A tool used for performing coverage-guided fuzzing. The fuzzing engine typically mutates inputs, collects coverage information, and adds inputs to the corpus based on new coverage. ClusterFuzz supports the fuzzing engines [libFuzzer](https://llvm.org/docs/LibFuzzer.html) and [AFL](http://lcamtuf.coredump.cx/afl/).
  </Accordion>

  <Accordion title="Job type">
    A specification for how to run a particular target program for fuzzing, and where the builds are located. A job type consists of environment variable values.
  </Accordion>

  <Accordion title="Minimization">
    A [task](/reference/glossary#task) that tries to minimize a [testcase](/reference/glossary#testcase) to its smallest possible size, such that it still triggers the same underlying bug on the target program.
  </Accordion>

  <Accordion title="Reliability of reproduction">
    A crash is reliably reproducible if the target program consistently crashes with the same [crash state](/reference/glossary#crash-state) for the given input.
  </Accordion>

  <Accordion title="Regression range">
    A range of commits in which a bug was originally introduced. It takes the form `x:y` where:

    - `x` is the start [revision](/reference/glossary#revision) (inclusive).
    - `y` is the end [revision](/reference/glossary#revision) (exclusive).
  </Accordion>

  <Accordion title="Revision">
    A number (not a git hash) that identifies a particular build. This number must increment with every source code revision. For SVN this can be the SVN revision directly. For Git you need a mapping from numbers to git hashes — the mapping number can start at `1` and increment, or use a date format such as `20190110`.
  </Accordion>

  <Accordion title="Sanitizer">
    A [dynamic testing](https://en.wikipedia.org/wiki/Dynamic_testing) tool that uses compile-time instrumentation to detect bugs during program execution. Sanitizers are best supported by the [Clang](https://clang.llvm.org/) compiler.

    Examples:

    - [ASan](https://clang.llvm.org/docs/AddressSanitizer.html) (AddressSanitizer) — typically the most important, reveals the most memory corruption bugs
    - [LSan](https://clang.llvm.org/docs/LeakSanitizer.html) (LeakSanitizer)
    - [MSan](https://clang.llvm.org/docs/MemorySanitizer.html) (MemorySanitizer)
    - [UBSan](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html) (UndefinedBehaviorSanitizer)
    - [TSan](https://clang.llvm.org/docs/ThreadSanitizer.html) (ThreadSanitizer)
  </Accordion>

  <Accordion title="Task">
    A unit of work to be performed by a [bot](/reference/glossary#bot), such as a fuzzing session or minimizing a testcase.
  </Accordion>

  <Accordion title="Testcase">
    An input for the target program that causes a crash or bug. On a testcase details page you can download a "Minimized Testcase" or "Unminimized Testcase" — these refer to the input that needs to be passed to the target program.
  </Accordion>
</AccordionGroup>
